# Liquid Glass feature audit: Apple platforms and the web

Research date: **2026-10-10**. Baseline audited: **`8178b08`**, before this iteration. This is a feature-gap map, not a claim of native rendering parity. Check [API.md](API.md) and [VALIDATION.md](VALIDATION.md) for the current shipped API and browser evidence.

## What the earlier preview missed

The preview implemented a portable glass surface: blur, saturation, fixed fill/shadow, rounded edges, light/dark appearance, a pointer-following highlight, accessibility fallbacks, and optional SVG displacement. That is a useful material foundation. It did not yet implement most of the **behavioral system** surrounding Apple's material: contextual legibility, touch feedback, changes in material thickness, coordinated glass shapes, and separation beneath floating navigation.

The most consequential new finding is that Apple has continued refining the design. In its **WWDC26 Platforms State of the Union**, Apple describes stronger diffusion of complex backgrounds, a darkened edge and brighter specular highlights, a continuous appearance slider, and a uniform toolbar background when content scrolls underneath. These are changes to material readability and user control, not simply more refraction. [Apple, WWDC26/102](https://developer.apple.com/videos/play/wwdc2026/102/)

Apple's current iOS page describes more uniform refraction and improved contrast. It is labeled an iOS 27 preview when fetched; this audit does **not** infer a shipping date from it. The current iPhone User Guide independently documents a slider in **Appearance → Liquid Glass**: moving it changes material tint/transparency. The user's chosen material density is distinct from a developer's semantic tint color and from SwiftUI's regular/clear variants. [Apple iOS overview](https://www.apple.com/ios/), [Apple iPhone User Guide](https://support.apple.com/guide/iphone/adjust-iphone-display-and-text-settings-iphd6804774e/ios)

## Prioritized work

1. **Material strength and legibility.** A bounded continuous density/opacity preference is the highest-value current-generation gap. Add explicit backdrop-tone input and semantic tint separately. Strength must not disable the existing solid/contrast fallback; “automatic appearance” must keep its documented meaning. Demonstrate bright, dark and busy backgrounds, with actual labels rather than empty shapes.
2. **Real input feedback.** Pointer movement alone is incomplete on phones. Add localized press illumination and restrained deformation for native buttons, including touch and keyboard. Reset correctly on cancel, pointer loss, blur, disabled states and controller destruction. Do not intercept clicks or change hit targets. Motion preferences need immediate enforcement.
3. **Navigation separation.** Replace the whole-element masking suggestion with a dedicated, noninteractive scroll-edge layer. Support soft fade and hard backing. Floating controls and their focus rings must remain unmasked; content should remain readable outside the intentional overlap region.
4. **Geometry transitions and grouping.** Add a small opt-in helper for a single decorative glass backing moving between semantic targets. Stable identity, interruption, disconnected elements and reduced-motion fallback matter more than an impressive standalone animation. Shared backing is useful now; arbitrary merging/refraction should remain a clearly separate future tier.
5. **Evidence and integration coverage.** Put each behavior in the demo and API/agent recipes. Validate touch cancellation, keyboard activation, dynamic preference changes, scroller boundaries, React/Vue updates and teardown. Record live-browser results separately from unit tests, and do not treat a CSS syntax check as optical rendering proof.

These priorities are an engineering assessment from this audit, not Apple's prescribed implementation for the web. The portable core can make these enhancements without a runtime dependency or importing DOM globals during SSR.

## Browser constraints that shape the API

`backdrop-filter` exposes a compositing effect, not a JavaScript-readable texture of arbitrary page pixels. Its nearest backdrop root limits which painted content participates; filters, opacity and masks in ancestors can change that region. The CSSWG Level 2 draft explicitly notes that the backdrop-root definition is not yet a consensus standard. A host-provided brightness hint is therefore more honest than claiming full automatic contextual adaptation. [MDN backdrop-filter](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter), [CSSWG Filter Effects Level 2](https://drafts.csswg.org/filter-effects-2/)

SVG displacement is a channel-driven pixel shift. Its general availability does not establish interoperable support for an SVG URL used as a live CSS backdrop filter. Our experimental lens also lacks native scattering, shared optical sampling, size-dependent thickness and color spill. Preserve the conservative gate and solid/CSS fallbacks; measure the resulting pixels. [MDN feDisplacementMap](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/feDisplacementMap)

Owned image/video/canvas renderers can do more sophisticated optics or luminance sampling, but introduce crop synchronization, texture ownership and origin restrictions. Reading a canvas after drawing cross-origin content without CORS approval is blocked. A copied-background demo does not prove an arbitrary live DOM renderer. [MDN canvas origin restrictions](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image)

Reduced-transparency detection has limited browser availability, so explicit application preferences remain necessary. Motion, contrast and forced-color settings must override new effects. Native semantic elements matter in forced colors because browsers choose some system colors using element semantics, not merely an ARIA role. [MDN reduced transparency](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-transparency), [MDN reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion), [MDN contrast](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-contrast), [MDN forced colors](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors)

## Scope and source method

This investigation used Exa for **90 search results across nine queries**, covering native material behavior, custom effect APIs, 2026 refinements/settings, and browser constraints. Search results were candidate sources, not validation. Apple Developer session transcripts, API pages and the iPhone User Guide were fetched and compared against the actual source code. Third-party reproductions, product marketing comparisons and community support replies were excluded as authority for native feature claims.

WWDC25 sessions are dated June 2025; WWDC26 sessions are dated June 2026 in search metadata and identify their event in the fetched page. Live API/Support pages have no reliable publication date; the access date above is the relevant context. Copyright footers are not publication evidence. The HIG Materials landing page was discovered but its fetch returned only the page shell, so detailed feature claims here rely on the fetched Apple transcripts and API documentation instead.

Complete native parity would require Apple's private compositor behavior and native system integration. This project should aim for an independently implemented, accessible web material and useful interaction primitives, with accurately named approximations and visible remaining gaps.

## Changes shipped by this iteration

The behavior preview adds bounded fill strength and hex tint, explicit backdrop tone, touch/keyboard press feedback, a moving decorative backing helper, and actual scroll-boundary-aware soft/hard scrims. It also fixes adapter tag replacement, custom-element option coverage and renderer fallback reporting. These address portable parts of priorities 1–4; the feature matrix above intentionally retains its pre-iteration baseline for auditability.

The opacity setting multiplies the variant fill; it does not reproduce Apple's continuous scattering/tint compositor. The tone hint is supplied by the app, not captured from DOM pixels. Indicator movement changes measured rectangle bounds, not optical union. See API.md, CHANGELOG.md and the /behavior/ demo for the precise current contract. Automatic pixel sampling, content-aware shadow, native thickness, ambient color spill, shared optical sampling, arbitrary merging/materialization, navigation minimization and OS-specific integration remain gaps.

## Motion preview follow-up — 0.3.0-preview.1

The next iteration adds reusable spring press/release, directional deformation, interruptible spring selection bounds and presentation entry/exit transitions. Motion is optional in core, React, Vue and the custom element; explicit/system reduced motion snaps to the target. See [MOTION_RESEARCH.md](MOTION_RESEARCH.md) for primary Apple references and [the motion lab](https://wpsydev.github.io/liquid-glass-kit/motion/) for actual controller-driven examples.

These implement portable animation behavior, including velocity-preserving retargeting. They do not reproduce native materialization, shared optical sampling or arbitrary shape merging. The baseline matrix remains historical. The core still lacks automatic background-pixel sampling, content-aware shadow, size-dependent scattering, ambient color spill, navigation minimization and OS integration.

## Owned-scene optics follow-up — 0.4.0-preview.1

An optional WebGL2 scene renderer now supplies screen-space procedural wallpaper and analytic rounded-rectangle edge refraction. This closes a narrow experiment gap for applications that own the entire rendered background; it does not supply arbitrary DOM background capture, physical shape union, native optical parity or external texture support. The ordinary CSS path remains the portable default. See [SCENE.md](SCENE.md).

## Mobile design follow-up — 0.5.0-preview.1

The mobile iteration adds originating-pointer ownership, nested semantic-control isolation, progressive continuous CSS corners, coordinated inner-radius tokens, coarse-pointer hover cleanup, and safe-area/dynamic-viewport/44px target helpers. The mobile studio composes real springs with native navigation, a range and a scrollable form sheet. [MOBILE_RESEARCH.md](MOBILE_RESEARCH.md) connects these decisions to primary Apple and web-platform sources; [MOBILE.md](MOBILE.md) teaches agents how to apply them.

These are independent web adaptations. The superellipse is not Apple’s measured native curve; unsupported engines retain round corners and optical maps remain round. Responsive Chromium checks do not establish physical iOS Safari behavior, native haptics, hardware-radius detection, keyboard geometry, optical merging or private compositor parity.
