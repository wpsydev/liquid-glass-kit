# Resource 05: Kage

Reviewed 2026-10-11 using Exa and the native T3 browser. This is inspiration and workflow research, not an integration claim.

## Observed evidence

- https://kage.design/ organizes references by component kind, product, page, visual style, industry, color and stack. This provides more useful selection context than a single collection of effect names.
- https://kage.design/designs/sineframe-m3-landing-page separates a full-page brief from ten extracted component references. Its public analysis emphasizes restrained color for pass/fail semantics, alternating content bands and realistic product artifacts. The reference is not a performance benchmark.
- https://kage.design/designs/thinking-orbs-landing-page describes a component-state gallery, contextual use, installation and API reference around one focal animated object. This is useful evidence for documenting states and intended use, rather than shipping isolated decoration.
- https://kage.design/mcp-setup documents `design_brief`, `search_designs`, `get_design`, `get_component` and `list_taxonomy`. The remote endpoint is account/keyless with normal rate limits. No server was installed or called in this research.
- https://kage.design/skills distinguishes interface, motion, review and workflow skills. Third-party repositories have their own licenses; listing them does not imply endorsement or compatibility.

## Independent feature proposal

The implemented optional typed integration planner exposes `listGlassPatterns()` and `createGlassIntegrationBrief({ task, stack, widgets, motion, optics })`. It uses one authoritative local recipe manifest to return supported entrypoints, exact imports, semantic controls, required interaction states, host callbacks, experimental boundaries, fallback behavior and a validation plan. Accessibility and performance appear as concrete acceptance checks and host responsibilities, not invented configuration fields.

This is distinct from the DESIGN.md exporter: it describes how to integrate working behavior, not a product's visual token identity. Keep its output original and tied to implemented APIs. A briefing artifact does not execute an agent or guarantee the agent reads it. Do not generate instructions for nonexistent registry packages.

The original Integration Desk demo supplies three reusable contexts: a reading workspace, an agent workspace and a product story. Users can edit the actual task, choose HTML/React/Vue/Svelte/Next.js/Astro, select working library widgets and choose none/subtle motion plus CSS or explicit experimental owned-scene optics. Its Steps, Imports, Checks and Markdown views are produced by the actual typed utility; native clipboard and file download export the current brief. No remote design service or agent is executed.

## Performance and verification

Pure, SSR-safe optional utilities; no root/runtime dependency or background work. Return structured data and deterministic Markdown. Bound input/output size, cache static recipe metadata, reject unavailable widget names and benchmark generation with explicit recipe counts. Keep package size, generation time and browser rendering as separate measurements. Validate each generated import against current package exports and each lifecycle statement against the actual controller API.
