## Concrete current workflows

- [Design mode](https://v0.app/docs/design-mode) operates against a running preview: explicit inspect/interact modes, element selection, pending style/content edits, undo/redo/reset and before/after comparison. Apply serializes edits/instructions and produces a new chat version for review/reversion. Current product restrictions include latest preview/runtime/version, no read-only chats and no mobile viewport support. These are v0 restrictions, not a reason to disable our own ordinary mobile controls.
- [Design Systems 2.0](https://v0.app/docs/design-systems-2) imports verified package/source/consumer references, checks a starter and saves a skill only after review. Its version-1 v0.json contains referenceWorkspace sources and starter selection; up to three read-only GitHub sources are documented. Existing generated projects do not automatically migrate when a saved skill changes.
- [API design systems](https://v0.app/docs/api/v2/guides/design-systems) documents explicit skills entries for memory/remote/project scopes. [API overview](https://v0.app/docs/api) currently uses SDK `v0.chats.create`, result data/error, authenticated previews and backend-owned authorization. [Design Mode API guide](https://v0.app/docs/api/v2/guides/design-mode) explicitly says its model translates descriptions to source edits; selectors/previous values are context, not checked preconditions. Our deterministic material draft revision checks therefore do not claim to reproduce v0 source-edit behavior. None of those services is installed, authenticated or callable as our library integration here.
- [Legacy design systems](https://v0.app/docs/design-systems) now points to 2.0. Do not base current recommendations only on registry-based imports. Source 19 already proposes our original registry, source 2 tokens/contracts and source 38 scoped guidance packs; another metadata export would duplicate them.

## One distinct independent feature

**Staged material draft controller** for an original local inspector, not a clone of v0's editor/runtime. `resolveOptions` currently normalizes material options and attachGlass.update replaces configuration; examples directly mutate previews. They lack reusable pending-edit history, before/after and explicit host commit/conflict semantics.

Suggested `createGlassMaterialDraft({ initial, revision, onPreview, onCommit })` with `patch(options)`, `undo()`, `redo()`, `preview('before'|'after')`, `reset()`, `commit(expectedRevision)`, `cancel()` and a readonly draft/history/status snapshot. Operate only on the library's known material options, not arbitrary CSS, DOM selection or code edits. Capture full normalized option snapshots so replacement updates do not accidentally erase unchanged fields. Reuse canonical option validation/defaults and cap history, patch count and metadata lengths.

The host explicitly binds a draft to an owned surface/controller and decides how to save or generate source. Preview events carry actual options; commit requests carry base revision plus final options. A stale external revision must report a conflict rather than silently overwrite newer changes. Deduplicate an in-flight commit, preserve failure/retry state, reject stale completion results and define cancel/reset behavior without pretending to cancel an already executed backend action. A committed host result is distinct from a requested Apply. No model call, filesystem write, v0 API or remote persistence occurs in this core.

Before/after temporarily changes the preview, not the history baseline. Undo/redo apply to pending edits before commit; source 27's undo window instead reverses an already applied host operation. Source 2's design contract is an authored export, not an interactive draft. Full UI can use existing field, numeric, sequence and feedback tools; no new giant inspector or compulsory React editor dependency is necessary. React's existing adapters render their own native elements and preserve class/style; wrapperless third-party composition is another possible future gap, not this feature's scope.

An original native inspector demonstrates selected owned surface, several real parameter changes, undo, comparison, Apply and a visible new host revision. Controls are ordinary labelled 44px/16px inputs, with reduced motion and solid modes. Applied CSS/source must be shown as host output rather than claiming an actual edited external app. Do not intercept every click on the page or replace application semantics with editor overlays.

## Technical/performance boundaries

Use pure copies/bounded history and callbacks on explicit edits, not geometry polling or an idle frame loop. Expensive blur/map rebuilds should not run for every slider pixel by default; host may coalesce live previews and commit once. Surface replacement/unmount clears its binding without mutating unrelated controllers. No snapshot contains arbitrary form data, DOM HTML, screenshots or credentials. SSR module imports remain safe; actual preview attachment is host-owned.

Tests should check patch preservation, history bounds/branching, comparison without baseline mutation, stale revisions, pending commit rejection and failure/restore. Browser work must verify actual target updates, preserved controls, one controller per surface, contrast/preferences and mobile layout. A state-unit test is not evidence of DOM/source editing or a v0 integration.
