# Resource 20: shadcn/ui

Reviewed 2026-10-11 with Exa and native T3 preview. Introduction, two public component documentation/live-example pages, explicit Base UI/Radix variants, repository license, and primary form/accessibility guidance were inspected. No CLI install, account, commercial kit, or copied source/assets were used.

## Two concrete public examples

- https://ui.shadcn.com/docs/components/field redirected in the native browser to https://ui.shadcn.com/docs/components/base/field. Its payment/address, input, textarea, checkbox, radio and responsive-layout examples show a consistent anatomy: label, real control, description and error inside a field; related controls use fieldset/legend. The documentation distinguishes vertical, horizontal and container-aware responsive orientations, and separates wrapper invalid styling from the input's `aria-invalid`. Live sampled Name/Card Number/CVV controls had associated native labels, 14 px text and 32 px height. The adjacent card-number help paragraph was present, but the sampled input had no `aria-describedby`. This is an observed association gap in these examples, not a blanket accessibility verdict on the project.
- https://ui.shadcn.com/docs/components/input-group redirected to https://ui.shadcn.com/docs/components/base/input-group. Examples include search/result addons, password controls, prefix/suffix text, textarea headers and action footers. Documentation specifically keeps the input/textarea before addons in DOM and positions addons visually through inline/block alignment. The live first group followed that order: input, icon addon, results addon. Its input had a placeholder and no native label in the sampled DOM; many later alignment examples did have explicit labels. Sampled text fields again used 14 px text and roughly 32 px height; textarea examples were about 64 px high. A placeholder or search icon must not become our default substitute for a proper accessible name.

https://ui.shadcn.com/docs/components/radix/field documents a separate primitive family. The public generic route's current Base UI selection is not proof that all installed shadcn projects use Base UI or that Radix and Base UI controls share every implementation detail. https://ui.shadcn.com/docs describes open-code distribution, composition and agent-readable interfaces; importing the whole stack is unnecessary for our native field enhancement.

## Distinct independent feature

Add an optional native-field semantics helper and matching scoped CSS. Suggested API: `attachGlassField(control, { label, description, error, invalid })`, returning `setError(message)`, `update()`, `clearError()` and `destroy()`, with a pure `getGlassFieldAttributes(...)` companion for SSR/controlled adapters. The first release can explicitly support one authored native input, textarea or select per field; grouped radios/checkboxes should retain native fieldset/legend recipes rather than pretend every group is a single text field.

Require a stable ID for explicit labels, generate deterministic IDs only through a host-supplied strategy, and validate same-document relationships. Merge description/error IDs with preexisting `aria-describedby` tokens without deleting unrelated hints. When an error clears, remove only the helper's error reference; a hidden error's text can still be included in an accessible description if its ID remains referenced. An optional `aria-errormessage` enhancement must not replace the more broadly useful description association without actual assistive-technology evidence. Never overwrite an authored accessible name simply to make a decorative wrapper look complete.

Set `aria-invalid` on the actual control and an independent wrapper attribute for styling. Render error content as text, not arbitrary HTML. The host owns validation rules, touched/submitted state, async results and server messages. Preserve native type/required/min/max/autocomplete/inputmode constraints and browser validation. Do not clear or replace a host's custom-validity message by default. Client helpers are not server validation or authentication. Avoid reporting every untouched empty required field as an error immediately on mount.

CSS can provide stacked mobile layout, logical inline/block addon placement, focus-within framing, a readable invalid state, 44 px control/action targets, 16 px text inputs, and solid/forced-color fallbacks. Keep the native control early in DOM; icon/action addons need their own names and native buttons. Do not put a blanket click-to-focus handler on an addon group that steals focus from buttons or disrupts selection. Avoid nesting unrelated focusable controls inside a text label. Labels remain visibly useful and clickable; help/error strings remain concise and adjacent.

A form-level error summary, if offered later, should link to specific controls and have deliberate announcement/focus timing. The initial field helper should not steal focus or install a competing submit handler. This differs from source 04 composition (layout only), source 16 action lifecycle (operation results), and source 19 registry distribution (files/dependencies): it adds correct per-control description/error relationships and useful native field presentation.

An original showcase can use workspace settings, a prompt composer, and a deployment URL field, with real labels/help, a controlled local invalid URL, clear recovery, and logical addons. Do not copy the payment example or promise encryption/security from a decorative form. Mark any submission explicitly local/simulated unless a real host service is connected.

## Primary references and performance

- https://www.w3.org/WAI/tutorials/forms/labels/ explains native label associations and why placeholders/icons do not replace labels.
- https://www.w3.org/WAI/tutorials/forms/notifications/ covers clear inline errors, linked summaries and deliberate overall feedback.
- https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-describedby documents space-separated same-document ID references and notes that referenced hidden text still contributes to the description.
- https://developer.mozilla.org/en-US/docs/Web/HTML/Constraint_validation documents semantic input constraints, validation APIs and the continued need for server validation.
- https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:focus-within supports authored group framing without JavaScript focus polling.

No React, Base UI, Radix, form-state library, schema validator, icon set or animation engine belongs in the portable helper. Pure SSR attributes need no browser globals; mounting updates a small fixed set of attributes/text nodes. CSS focus state needs no RAF or geometry reads. Optional input/blur validation should be explicit, coalesced and host-owned rather than a deep observer of every field subtree. Use one material surface for the group, not multiple nested filters. Reserve sensible error space only where the authored layout calls for it, without clipping long translations or imposing oversized blank regions globally.

Test existing IDs/labels/descriptions, duplicate/invalid IDs, unrelated ARIA tokens, multiline errors, text injection, invalid clearing, updates while focused, authored custom validity, RTL/addon order, native selection/autocomplete, destroy restoration, SSR and controlled React/Vue integration. Validate small screens and text enlargement separately from unit tests; desktop browser emulation does not establish real iPhone assistive-technology behavior. Benchmark attribute/text work separately from expensive host validators and framework rerenders.
