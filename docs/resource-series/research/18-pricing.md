# Resource 18: Pricing Pages

Reviewed 2026-10-11 with Exa and native T3 preview. Public gallery entries, two current destination pages, relevant official product documentation, gallery legal terms, and primary formatting/accessibility references were inspected. Discovery returned four candidates. No subscription, account creation, payment, or remote form submission occurred.

## Two concrete examples

- https://pricingpages.design/sites/n8n records a pricing page added October 15, 2025. https://n8n.io/pricing/ currently explains that plans are priced by monthly workflow executions, not steps, workflow complexity, or users. It separates Starter/Pro/Business/Enterprise cards, cloud/self-hosted availability, and detailed feature comparisons. Keyboard-focusing its native billing input and pressing Space changed checked state and immediately updated displayed amounts and the billed-monthly wording. The initially inspected annual Starter amount was 20 euros/month; switching showed 24 euros/month billed monthly. These are time-specific observations, not pricing advice or values to bake into our demo.
- https://pricingpages.design/sites/lyssna links https://www.lyssna.com/pricing/. The live page distinguishes Free, Growth and custom Enterprise, has annual/monthly choice text, plan limits, and a comparison section. It explicitly says participant-panel responses are priced separately on every plan. Its annual headline displayed USD 166/month. Official https://help.lyssna.com/en/articles/4953377-plan-and-pricing-overview instead displayed USD 165/month with USD 1,990 billed annually. The two rounded monthly displays differ; the actual annual charge must be modeled separately rather than reconstructed by multiplying a rounded headline by twelve. No conclusion about the checkout amount was inferred.

Pricing design is information architecture: billing interval, units, included limits, optional costs, and hosting restrictions matter as much as card appearance. The gallery's About page makes conversion claims without presenting experiment results applicable to our framework.

## Distinct independent feature

Add a dependency-free, SSR-safe pricing model and view-data formatter, for example `createGlassPricingModel({ locale, currency, plans, periods })` and `resolveGlassPrice(planId, period)`. Keep rendering host-owned with native controls and authored semantic tables/cards. The module validates declared values and returns structured labels/amounts, not HTML strings or invented commercial promises.

Suggested variants: free, recurring fixed charge, usage-priced quantity, and contact-sales. Store authoritative charges in integer minor units with a declared currency/precision and billing period. Distinguish invoice total from monthly-equivalent display, setup fees, optional usage, and plan limits. Avoid arbitrary floating-point money accumulation; reject unsafe integers and invalid/overflowing calculations. If fractional equivalents require rounding, expose an explicit documented rounding policy and retain the exact billing total. Support currencies with zero or three minor digits instead of universally dividing by 100.

Calculate comparative savings only when currency, charge unit, quantity, included scope and equivalent time horizon match. Compare annual charge against twelve comparable monthly charges; do not compare a rounded monthly-equivalent headline against a different usage tier or count optional costs as included. A custom/contact-sales plan is not zero dollars; an unknown price is not Free. Labels like Most popular, no card required, refund guarantees, and limited-time offers must remain explicit host claims, never generated by the model.

A monthly/annual choice should use labeled native radios/selects with unchanged focus and a concise result announcement. Feature comparisons should remain a real data table when comparing rows/columns. On narrow screens, provide a bounded horizontal scroll wrapper and/or a genuinely accessible alternative rather than stripping header semantics from arbitrary div grids. Use explicit locale in both server and client output to prevent hydration mismatches. The host owns taxes, discounts, exchange rates, contractual terms, checkout, billing and confirmation; this UI helper is not a financial ledger or payment engine.

This differs from design-contract export, integration briefs, layout composition and source 16 action lifecycle: it adds coherent billing semantics and deterministic display data. An original showcase can use clearly fictional demo plans, a real interval radio group, visible annual invoice totals, and a readable glass comparison table. Every displayed savings badge must match the supplied model.

## Primary guidance and performance

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat documents locale-aware currency formatting and different currency minor-unit conventions. Runtime default locale is not deterministic across SSR/client environments; cache a bounded set of explicit formatter configurations.
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/isSafeInteger documents exact integer bounds and why larger values require a different representation. Safe inputs do not imply every derived multiplication or float conversion is safe; check intermediate results too.
- https://www.w3.org/WAI/tutorials/tables/ explains captions, row/column headers, and scope/id associations in comparison tables.
- https://www.w3.org/WAI/ARIA/apg/patterns/radio/ explains mutually exclusive choice behavior. Prefer native radios rather than rebuilding their keyboard model for a decorative billing toggle.
- https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html supports concise non-focus-stealing updates; do not announce the entire comparison table after every interval change.

Pure calculations need no browser listeners, frames, requests or runtime dependency. Construct formatters once per bounded configuration, not per cell per render. The optional demo interaction should update only changed price/copy nodes and preserve focus. Do not blur hundreds of comparison cells independently or animate table geometry. Test free/custom/usage variants, zero values, currency precision, invalid data, unsafe intermediate arithmetic, nondivisible annual amounts, incomparable plans, explicit locale, missing prices, and annual-toggle focus/announcement behavior. Benchmarks must measure formatter/model work separately from framework rendering. No conversion or revenue improvement follows from the helper alone.
