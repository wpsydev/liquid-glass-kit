## Distinct independent feature

Add a pure, optional registry-item builder/validator for our own original integration recipes, plus a small machine-readable recipe index. Suggested API: `createGlassRegistryItem({ name, title, description, author, files, dependencies, registryDependencies, meta })` and `createGlassRegistryIndex({ name, homepage, items })`. Return deterministic JSON data; do not fetch remote source, read arbitrary disk files, install packages, execute commands, or publish from this library helper.

Target an explicitly documented subset of the official shadcn registry schema, such as authored `registry:lib`, `registry:style`, and optional React `registry:ui` recipes. Mark framework/runtime requirements precisely. Portable CSS and native-controller recipes must not pull React, Motion, Tailwind, Radix, icon sets, or a schema runtime into our core. Optional adapter items may declare required peers and package dependencies honestly. The exported index can reference original previews, docs, import entrypoints, license/attribution and accessibility/performance boundaries through clearly named metadata.

Validate stable unique names, a finite item/file count, bounded content strings, duplicate file destinations, compatible file types, and declared dependencies. Our first export should permit only relative project destinations under a host-authorized scope. Reject absolute paths, drive letters, traversal segments, home-directory targets, secret/config destinations such as `.env`/`.npmrc`, and control characters. The upstream format permits powerful file targets; implementing a smaller safe export subset is an intentional limit, not full-schema equivalence. Do not describe validation as a sandbox for arbitrary registry code or npm lifecycle scripts.

Pin our own recipe/package versions and distinguish development dependencies from runtime requirements. Do not imply that bare dependency names refer to the same private registry; the official spec gives them built-in semantics. Use explicit namespaced/URL addresses where appropriate, without putting credentials in generated URLs or committing tokens. Include required license text/attribution when a genuinely licensed third-party dependency is used. Hosting must serve only verified built records; a generated path/URL is not a published artifact.

This is distinct from source 02 design-contract export and source 05 integration briefs: those express design/integration intent, while this feature specifies an installable set of original files and dependencies. An original demonstration can show a recipe inspector, dependency-free portable item, optional React item, and rejected unsafe target. It can display/download local JSON before any real CLI installation; label that scope truthfully. Actual shadcn CLI install validation remains a separate developer integration check, not proof supplied by a serializer unit test.

## Primary references and performance

- https://ui.shadcn.com/docs/registry/registry-item-json defines item/file types, dependencies, CSS variables, and target paths. It explains that dependency refs are not inherited; reproducibility requires explicit pins on each dependency.
- https://ui.shadcn.com/docs/registry/registry-json defines the registry index shape.
- https://ui.shadcn.com/schema/registry-item.json is the official machine-readable schema. A dependency-free validator should truthfully claim only its supported subset; full upstream-schema validation can be a development-only check.
- https://www.rfc-editor.org/rfc/rfc9727.html describes API catalogs. 21st's separate ARD document is platform resource metadata; do not label it a universally implemented discovery standard or invent unsupported API/MCP entries for our static site.

Generate finite immutable records on demand, with linear file validation and bounded serialization. No DOM/runtime listeners, idle frames, third-party network requests, or large catalog payload belongs in the root material bundle. Keep exporter/manifest types in an optional entrypoint and split per-item HTTP records at hosting time. Benchmark input validation/serialization and payload size separately from an external CLI's dependency install/build time. SSR-import tests, deterministic ordering, malformed paths, conflicting targets, empty/oversized content, and actual install in disposable representative projects are relevant checks.

It restricts automated scraping, redistribution/metadata republication and media reuse, and requires rights and attribution when publishing. The two observed MIT records do not grant blanket rights to their marketplace previews or catalog. Notes here are limited original analysis with source links, not an exported marketplace dataset or copied titles/descriptions/tags. Do not reuse screenshots, generated videos, source implementations, paid templates or branding. Our registry items and demos should be independently authored.
